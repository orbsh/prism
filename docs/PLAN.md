- [ ] Phase 1.10 — Fluxen integration (ADR-0017 §8; the connection plane's own front end). The delivered front end is a fluxen bundle served from `/assets/` as plain downloads on the same accept loop as `/ws` and `/code` (no event semantics — §8), and it speaks the SAME event protocol as every other client on `/ws`: one connection, one frame shape, no second RPC surface. Two client events define the contract; both are ordinary events on the persistent socket (§4 — "action" is retired, `login` is not a separate HTTP round trip).
  - `init` — the client's first event after connect, emitted once its bundle is up (the page knows when it can render; a push on connect would race the boot). It asks the connection plane for the application's layout, and the answer carries the layout itself (the Accrete root) — the page renders its skeleton from that and from nothing else. This is the client-side twin of §8's envelope-shaped view events: the layout is DATA on the wire, the front end is a renderer with no baked-in application shape. A booth answers: the event dispatches exactly as every other client event does (the client's `ev` names the booth TYPE, the handler returns the layout value — the echo plane's multi-entry model, no special case, no gateway verb for this; `ping` stays gateway-liveness only).
  - SOURCE RULED 2026-10-29 (`PRISM_INIT`, a deployment fact — declared, never defaulted; two legal forms): `file:<path>` — prism reads the document at boot (YAML or JSON; YAML is a superset, so one parser covers both) and answers it verbatim; `event:<type>/<handler>` — the event is submitted to the realm on the booth type's SINGLETON instance (a GLOBAL booth: one instance for the whole venue, not one per connection, because a layout is not per-client state) and the handler's return value is the answer. Both deliver the layout to the asking connection as ordinary `create` frames and close with an ack `init.result {frames: N}` — the layout IS the first view operation, so the client's rendering path does not branch on where it came from and needs no layout envelope. A third form, `webhook:<url>` (prism fetches the JSON and relays it), is REFUSED by ruling: it is the previous generation's (Fluxora) shape; it puts a network fetch on the client's first event, adds a second deployment dependency and an operator-visible config surface, and it buys nothing a booth does not already do — a handler that needs the URL makes the HTTP call inside its own body. Absent `PRISM_INIT` is legal: `init` answers the standard error VALUE naming the config, and the rest of the plane serves normally; the boot line states which source is live.
  - `login` — the event itself EXISTS (Phase 1: signup/login on the same socket with argon2id in prism's own okm instance, the connection's auth field written; §2/§4). What is NEW is the client half: the login form rides the layout `init` delivered, the form emits `login`, and the answer (`login.result`, or the standard error VALUE with the socket staying up) is the page's only auth channel — there is no second round trip to fall back on. On reconnect the stored device anchor restores the binding (`?device=`, §2), so the front end must not present a login form the anchor already answers.
  PARTIALLY LANDED 2026-10-29 (the wire and the static face; the application half is next): `crates/prism/src/assets.rs` serves the bundle on the shared accept loop (`/assets/<rel>`, entry document at `/assets` and `/assets/`, canonical-root check, no listing, hashed names immutable — `tests/ui_leg.rs::assets_are_plain_downloads_on_the_shared_loop`). `crates/prism/src/ui.rs` is the renderer leg at `/ui` speaking fluxen's `content` wire (Message down, Outflow up; `connected` as an `ev != draw` frame; `init` answered by the layout frames + an empty `init.result` terminator; a deployment with no source answers `init.error` instead of hanging). `crates/prism/src/init.rs` parses `PRISM_INIT` — `file:<path>` (YAML/JSON read at BOOT, list or single frame), `event:<type>/<handler>` (the booth's SINGLETON instance via `Gateway::call_global`), and REFUSES `webhook:` naming the ruling. `Deployment::from_env` carries both facts; the boot log states which faces are live and names an absent bundle. The leg split is now physical: `/ui` = the renderer, `/ws` = the programmatic leg (CLI/peers/tests), one shape per leg — the earlier phrasing that put Accrete on `/ws` was wrong and the ADR Update says so. DISPATCH + IDENTITY LANDED 2026-10-29 (same day, second cut): every uplink is now an answer — verbs first (`login`/`signup`/`logout` write the leg's auth field and answer `<verb>.result` with the identity in `sender`: `user:<id>` or `device:<id>`; failures answer `error`), then the booth NAMED BY THE EVENT (the peer leg's rule: type == handler == `ev`), instance `Named("channel")`, payload `{sender:{device,user}, args}`; its answer is normalized to VIEW FRAMES and terminated by `<ev>.result`. The per-event auth gate reads the same persisted `interface_schema.auth` block as the peer leg, BEFORE the call; anonymous senders get `error` and the socket stays up. THE ENVELOPE LEFT THE WIRE 2026-10-29 (sixth cut, after fluxen `460d867`): downstream on `/channel` is now THE ACTION LIST — `Vec<Content>`, a JSON/CBOR array, always — and a map is refused at the renderer's boundary (`frame is an envelope, not an action list`). So this leg has no verbs left, and the venue's own speech became OPERATIONS: `inject` (fluxen ADR 0011) into `identity` (connect / `signup|login|logout.result`, `{device, user}`) and `notice` (`error` with `detail`, `init.error`, `turn.done`, `turn.error`). A layout binds both with `kind: local`. Removed with the envelope: `ev != "draw"` frames, `<ev>.result` terminators, `init.result`. A booth answer and the pushed layout each go out as ONE batch (order inside a batch is semantics: a region's `set` precedes the patch that fills it). `tests/ui_leg.rs` rewritten to the new shapes (its helpers now assert a message IS an array), `docs/adr/0017` en+zh carry the supersession, and the duplicated stale paragraphs in that ADR are gone.
A BOOTH'S ANSWER HAS TWO LEGAL SHAPES 2026-10-29 (found by the port's own tests): operations are DRAWN; anything else is DATA and goes out as an `inject` into a slot NAMED BY THE EVENT, with the event name `<event>.result`. Dropping the non-operations instead — what the first port did — made a booth's answer vanish into the log, and the symptom was a client waiting forever for a reply that had been silently discarded (`echo_steel` hands back its call envelope, which is data, not frames). The wire did not grow a second protocol for this: a renderer has no verb channel, so the vals plane is the only place data belongs, and a layout binds `<event>` if it cares. It also restores something the retired `<ev>.result` terminator used to carry — that an answer ARRIVED — without the empty envelope.
THE VENUE'S SPEECH IS NOW EVENTS; THE UPLINK IS AN EMIT (2026-10-29, ruled "改，退场"): `IDENTITY_SLOT`/`NOTICE_SLOT` are gone — the venue says `view:identity` (`{device, user}`), `view:notice` (`{detail}`), `view:turn.done`, `view:turn.error` through its own prefix subscription, and the init layout rides the same plane (`view:layout`, payload = the action list) so the identity fact cannot arrive after it. The forwarder ignores payloads that carry `args` and no `data`: a page's own uplink is a REQUEST seen by the same subscription, and forwarding it would echo the input back.
THE UPLINK IS AN EMIT, THE PAGE STILL SENDS A BARE `dest`: prism reads `Outflow {dest, id?, data}` and emits `view:<dest>` with `{name, channel_id, sender, args}` — the marker is the venue's, and fluxen keeps its own vocabulary (`different consumers of a renderer make different sense of a name`). `sender` comes from the socket, never from the frame.
THE MARKER NEEDED A FRAMEWORK RULE, AND GOT ONE (aura): a declaration may name the body's entry point separately from the event — `ReceiveDecl.entry`, `receives: {view:echo_frame: {entry: echo_frame}}`, threaded through `booth` → `EventRouter` (both the engine's introspection arm and the registry's) → the instance's subscription/queue tuple → `QueuedJob.handler`. Without it the event name IS the handler name, and the delivery is dropped SILENTLY (measured: booth never ran, nothing logged). Two bugs surfaced while doing it: the registry path (`registry.rs` `router.on`) never saw the field at all, and a steel `(hash a b) "receives" c` closes the call early — the schema then fails whole, so the booth has routes AND no auth, quietly.
A BOOTH EMITS ITS ANSWER, EVEN IN TESTS: a delivery discards a return value, so `echo_frame`/`echo_gate` now `ctx.emit` an event carrying the operations they were handed. Tests that expect a booth's return value to reach a page cannot pass under this model — that is the model, not a regression.
A DELIVERY THAT CANNOT CALL ITS BODY IS NOW VISIBLE OVER HTTP: aura's delivery seam keeps the reply it used to drop, logs `delivery of \`<event>\` failed at entry \`<entry>\`` with the booth type, and pushes `DeadReason::DeliveryFailed` into the dead ring; prism serves that ring at `GET /admin/dead` (`[{event, reason, data}]`, plain HTTP on the same accept loop — the admin face is not a WS protocol). Case: `admin_nodes::a_failed_delivery_is_readable_over_http` — a steel booth declaring an entry its code does not define, an emit, then the row over curl-shaped HTTP.
DEVICE IS NOT A CHANNEL (ADR-0018): prism knows devices (connections) and users (accounts), both verified; a channel is a user-visible grouping owned by whichever booth implements the application, including whether it exists at all. `channel_id` therefore leaves this wire — until it does, the venue's own envelopes use it as a DEVICE address, and the fan-out comparison (`channel_id == conn.device`) is that same misnomer. A booth that emits a real channel number reaches nobody today.
WHERE THE LEG STANDS AFTER THE 2026-10-29 RULINGS: landed — the prefix route (`view:*`, wildcard singleton), the envelope with `name`/`channel_id`/`sender`/`data`, sender excluded from the fan-out, both payload shapes (operations drawn, data injected into the slot named by the event), the deleted `<event>.result`, and prism following fluxen's LIVE vocabulary (`Outflow.slot`, `InjectOp.name`, tree address `slot`, `BindVariant::Uplink{slot}`). NOT yet landed, and both are rulings rather than cleanup: (1) the UPLINK is still an `invoke` (`engine.call` to the booth named by the page) instead of an emit of `view:<slot>` routed by aura — the ruling says invoke is not this channel, so the dispatch face has to move, and with it the question of where the per-event auth declaration is enforced once delivery is by emit; (2) prism's own speech still rides the `identity`/`notice` slot constants and would become `view:identity`/`view:notice` under the one-vocabulary rule. A third, cheap, holds either way: fluxen may rename `slot`→`dest` again, so nothing here hardcodes a word it does not read from `content`.
THE DOWNLINK IS ONE PREFIX ROUTE, TWO PAYLOAD SHAPES 2026-10-29 (user ruling): everything UI-facing is `view:<name>` in BOTH directions — the marker is what stops a page from forging an internal event — so the venue subscribes to the prefix (`wildcard: true`, singleton) instead of naming events in advance. The envelope carries the route: `{name: "view:<recipient event>", channel_id, sender, data}`; the venue strips the marker, excludes the sender from the fan-out, and hands the payload on. An OPERATION LIST is drawn; ANYTHING ELSE IS DATA and goes out as `inject{slot: <name>, name: <name>, data}` — both are legal, and the validity check belongs downstream in fluxen, not in a host that would otherwise teach the page a second vocabulary. A Rust body is not told which event fired (the dispatcher consumes the concrete name), which is why the name rides the envelope — that is the emitter stating where it is sending, not the venue guessing.
THE INVENTED NAME IS GONE 2026-10-29: a booth answer that is not an operation list is DATA, and data has no path down the renderer leg — the venue does not name it (`<event>.result` is deleted). A booth that wants the page to see something emits `view:<name>` with the envelope that says which channel and who is talking; what remains at the call site is one diagnostic line, because an answer that draws nothing is otherwise hunted for in the renderer. Tests therefore observe dispatch through booths whose answer IS an operation (`echo_frame`, and `echo_gate` for the auth declaration), which also proves the gate opens instead of asserting it.
FLUXEN'S LIVE VOCABULARY IS NOT THE COMMITTED ONE 2026-10-29: the working tree purges the word `event` from the UI wire — `Outflow.intent`, `BindVariant::Intent{intent}`, `BindVariant::Local{intent}`, `InjectOp.intent`, and the tree address is `slot` everywhere (`Append/Remove/Patch.slot`, `create` addresses the root with `slot: ""`). prism, its tests and `gravitational-prism/layout/venue.yaml` follow the tree as it is on disk, not the last commit. Two consequences worth remembering: the uplink is `{intent, id?, data}` (a frame's tree address is `slot`), and the venue's own notice payload no longer repeats the name it is already carried by.

THE CONNECTION LIFECYCLE IS AN EVENT STREAM 2026-10-30 (user ruling; modelled in `docs/MODELING.md`): the venue reports what happened to a connection as ORDINARY PLANE EVENTS, not as an `init` verb and not as a file — `view:connect {device}` when a device's connection is established, `view:login {device, user}` when it binds to an account (signup included), `view:logout {device}` when the binding ends, `view:disconnect {device}` when the connection is gone. `view:init` is RETIRED with its reason: it named the venue's own act rather than the fact the application cares about, it implied "once", and it belonged to no pair. The naming rule is now explicit on this wire — FACTS are named as they happened (`connect`, `login`: the venue observed them, an application only has to know), REQUESTS are imperative (`view:turn.submit`: a client wants it) — which is why a lifecycle notice never reads like a command an application could refuse. THE TOKEN NEVER RIDES THE PLANE: it is the page's credential and the venue states it to the page on its own connection (`view:identity`); an application acting for a user addresses the DEVICE, and the venue's auth gate is what actually holds the permission.
THE INITIAL LAYOUT IS ANSWERED TO `view:connect`, BY WHOEVER DECLARED IT 2026-10-30: this is what makes several booths able to own one application. An ORCHESTRATION booth answers with the shell as an ISLAND frame — a layout framework whose named regions each carry the slots that will exist — and then emits the business events those regions are about; each interested booth answers by emitting its own layout into the slot prepared for it (a chat rack, a force graph, a settings panel) and keeps talking to that region. One description on both sides (the layout is emitted by the booth that owns the logic, so a part cannot draw differently from what it does), an open number of parts (a new booth joins by declaring the event; neither the venue nor the orchestration booth enumerates them), a part replaceable without touching the shell (regions are slots), and the same shape in one process or many. `PRISM_INIT=file:<path>` survives as the weakest form and is a REMOVAL CANDIDATE — a layout with no logic is still an answer its carrier can produce. `invoke` was REFUSED for this: it is CALL semantics (one named target, one answer the caller waits for), right for special cases and wrong for composition, where the trigger has to reach every interested booth.
MANAGEMENT IS A VIEW 2026-10-30 (the general pattern lives in `docs/MODELING.md`; its first instance is gravity ADR-0007): an application's administration is a layout plus events — a control emits the management event, the booth emits the frames that expand the section, its controls emit ordinary events. `/admin` stays the VENUE's own (node approval, device revocation: facts about connections, devices and the plane); no application's management ever appears there. An agent drives the same events with its own device — "operable by an AI" is a property of the shape, not an extra API.

## Identity: a token is the credential, a device is a name (landed)

The number prism used to hand out on connect was called a device, and it was neither: it was a
random per-connection value that could be revoked and expired — a TOKEN — and it doubled as the
only credential, so guessing one inherited a login. The two are now separate, and both are ids
in the okm sense (16 bytes, never text; `okm_core::Uuid7` / `Uuid4`).

| collection | ns | key | payload |
|---|---|---|---|
| `Account` | 50 | `Uuid7` | `username`, `nickname`, `password_hash` |
| `Device` | 51 | `Uuid7` | `user`, `alias`, `first_seen`, `last_seen`, `revoked` |
| `Token` | 53 | `Uuid4` | `device`, `user`, `issued_at`, `expires_at`, `revoked_at` |

- **No id mirror in any payload.** `scan`/`get`/`scan_keys` hand the key back, so a row does not
  repeat its own name; `HighWater` reduces retire with the watermarked ids.
- **The key is the id.** No `DeviceKey { id }` wrapper struct — `Collection<S, Uuid7, Device>`.
- **Device ids are server-issued** (`Uuid7`), never fingerprinted in the client: a browser cannot
  see hardware, and a canvas hash can collide. The user renames the device (`alias`); the UI
  always shows the alias, falling back to the id's text form.
- **The token is the only credential.** `?token=<uuid4>` resolves to `(device, user)`, slides its
  expiry on use (default 30 days, `PRISM_TOKEN_TTL`); login/signup ROTATE it (old tokens of that
  device are stamped revoked); logout revokes them all; `/admin/revoke` revokes by token, the
  device-level revocation keeps its meaning. `?device=` stops being a credential.
- **Anonymous connections still get a token**, or a refresh would lose the room they were in.
- **Text appears in exactly four places**: `username`, `nickname`, `alias`, `password_hash`.
- **Transport**: 16 raw bytes on the wire in CBOR; base64uuid text in a JSON codec — a 128-bit id
  as a JSON number loses precision in the browser (f64), so text is the only portable spelling.

### What leaves prism with this change

`turn.submit` / `turn.cancel` are not prism's verbs. gravity is a booth: it declares
`ui:turn.submit` and `ui:turn.cancel` itself. Everything that came with the verbs goes too —
`turns.rs`, `TurnConfig`, the turn executor registration, and the `say.<n>` region naming (slot
names belong to whoever writes the layout, and the caller states them in the request payload).

Local verbs after this: `login`, `signup`, `logout`. Anything else is `ui:<dest>`.

(`Token` takes ns **53**: `nodes.rs`, the effector node registry, already owns 52. Two collections
on one ns is not a compile error, so check `#[ok_ns(…)]` across the crate before claiming a number.)

### State

Landed in `identity.rs`, `lib.rs`, `ui.rs`, `admin.rs` and `tests/identity_e2e.rs`:

- the three tables are uuid-keyed, with `by_name` / `by_user` / `by_device` indexes, and no payload
  mirror; `devices_of(user)` is the "my devices" list (uuid7 order = first-seen order);
- `Gateway::identify` is the only place that decides an identity: a live token names `(device,
  user)` and slides; anything else is a fresh anonymous device that still gets a token, so the
  client always leaves with something to present;
- the auth field of a connection is `Arc<Mutex<UserId>>` (a 16-byte id does not fit an atomic);
- ids are TEXT on the wire and in JSON payloads (`channel_id`, `sender`, `connected`), and the
  `connected` answer now carries `token`;
- `login`/`signup` rotate and report the new token; `logout` revokes the set and issues a fresh
  anonymous one, because the old one just died.

Verified: `--lib identity` 4/4, `--test identity_e2e` 9/9 (rewritten to the token semantics: a
token restores the binding, a device id restores nothing, a revoked device's token is dead).

Still red, and why: `ui_leg` (2/12) and `echo_e2e` (4/8) read the identity fact with the old shape
— their helpers want a numeric `device`/`user` (`ui_leg.rs:55`, `echo_e2e.rs:77`). Fixture work,
not design. The turn verbs (`turns.rs`, `TurnConfig`, executor registration, `say.<n>`) are still
