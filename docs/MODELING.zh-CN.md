# Prism 建模 — 连接平面

连接平面的模型放在一处：参与者是谁、线上跑的是什么、谁给谁命名、状态住在哪里。它描述**形状**；每条裁决背后的理由在 ADR 里（0017 线协议、0018 设备）。本文与 ADR 冲突时，ADR 是记录，本文是缺陷。

> **语言：** [English](MODELING.md)（主） · [中文](MODELING.zh-CN.md)

## 参与者

| 名字 | 是什么 | 谁发的 |
|------|--------|--------|
| **device** | 一条连接的身份，也是场馆唯一认识的可达性 | 场馆，连接时发（`?device=` 让它在重连后延续） |
| **user** | 设备绑定到的账号；匿名是一种状态，不是另一种设备 | 注册表，`login` 时 |
| **token** | 命名 (device, user) 的凭据；页面只持有它，别的东西不主张身份 | 注册表 |
| **booth** | 平面上的应用实例：由一个名字声明，凭自己的 `@on` 声明得知发生了什么 | 应用，注册时 |
| **renderer（页面）** | 画收到的，上行发 `Outflow {dest, id?, data}` | 场馆（它就是页面的 origin） |
| **场馆（prism）** | 转发、加/剥标记、按声明闸门、向设备扇出 | — |

## 线协议

一套词汇，带标记。跨渲染腿的一切都叫 `view:<name>`；标记的作用是不让页面伪造内部事件，加与剥都是场馆的事——页面从不写它，也从不看见它。

| 方向 | 参与者写什么 | 上平面的是什么 | 收方看到什么 |
|------|--------------|----------------|--------------|
| 上行 | `Outflow {dest, id?, data}` ——一个**裸**名字 | `view:<dest>`，载荷 `{device, sender, data}` | 摊位按自己声明的 entry 被调用 |
| 下行 | `view:<name>`，载荷 `{name, device, sender?, data}` | 同一个事件 | 页面收到剥掉标记的载荷 |

下游有两种合法的载荷形状，由收方决定能拿它们做什么：

- **动作列表**（`Vec<Content>`）被**画出来**——永远是数组，一条消息一个数组；
- **其余一律是数据**，落到 vals 平面、注入以事件命名的槽位里，等同于页面自己发出那个名字。

一个批次内部的顺序是语义（某个区域的 `set` 必须在填充它的 patch 之前），所以消息在路上从不被拆分或重排。

**发送者听不到自己的事件。** 场馆把发送设备从扇出里排除，这正是页面自己的请求不会回到它身上的原因，也正是摊位自己想发给提问那台设备时、载荷里**不带 `sender`** 的原因。

## 谁寻址谁

**设备**是地址；**用户**可以通过绑定到它的设备被触达。这条线上没有 channel：channel 是用户可见的分组（群聊，或使用同一套机制的一对一对话），而分组是应用的业务——它自己存成员、自己回答「这个群里有谁」、自己把群变成一份收件人列表。场馆无法枚举群、无法校验成员，也不发 channel id（ADR-0018）。

## 应用本身就是视图

一个应用的**全部**表面——它显示什么，以及它怎么被配置——都是同样两样东西：布局与事件。管理面没有任何不同。

- **初始布局是推的，不是请求的。** 客户端无法知道自己何时就绪；场馆在连接时说明它有什么，客户端把它收到的画出来。
- **产出这份布局的是一个事件，既不是文件也不是一次调用。** prism 在连接建立时取到 device，合成并发出 `view:init`；哪个摊位声明了这个事件，就由它用帧作答。以部署内容供应一个文件仍然可以存在，但那是挣不到位置的形状：一个没有逻辑的布局，同样是它的载体能产出的答案（一个返回那些帧的摊位），所以文件形式是可移除的候选。
- **为什么用事件而不是 `invoke`。** `invoke` 是**调用**语义：一个具名目标、一个调用方等待的答案——特殊场景合适，用来组装就不合适。一个应用的不同部分归不同的摊位，触发必须是一个所有相关摊位都能收到的东西，各自用自己的帧作答。
- **后续布局是普通流量。** 应用随时发帧：对先前声明的槽位 `create`、`set`、`append`、`patch`。
- **展开是一个控件加一个事件。** 布局里放一个 `dest` 指向应用事件的控件（比如「管理模型」按钮）；事件抵达摊位；摊位发出创建或追加该区块的帧；区块里的控件再发事件。场馆分辨不出管理区块和聊天区，也从不被要求分辨。
- **所以每个应用没有自己的 admin 面**：没有 admin HTTP 动词、没有配置文件、没有第二个 origin。场馆上的 `/admin` 只关于**场馆自己**（节点审批、设备吊销）——关于连接、设备和平面本身的事。
- **程序也是客户端。** 自动化开自己的连接、拿自己的 device、提交同样的事件与同样的载荷；「可被智能体操作」是这个形状的属性，不是额外的 API。
- **布局是帧唯一能被校验的东西。** 一个槽位名就是「我的表面在这里读」这句话，而只有握着布局的一方能说这句话是否成立——这正是渲染里那些名字必须由供应布局的一方声明、而绝不由往里画的执行器去猜的原因。

## 岛式组装：一个应用由多个摊位拼成

这个模型存在的理由，展开说。

一个**编排摊位**发一个岛模式的帧：一个布局框架，上面是若干具名区域，每个区域里预先放好将来会存在的槽位。然后它发出这些区域所对应的业务事件。声明了某个事件的摊位，用自己那一块布局作答、落进为它准备好的槽位——一个聊天区、一张力导向图、一块设置面板——此后直接与那个区域对话。

这为什么是一个模块化的论断，而不只是「帧可组合」：

- **一份描述，两侧共用。** 一个区域显示的布局，由它背后逻辑的所属摊位发出，于是这一块不可能画得与它实际做的事不一致——根本不存在第二份会漂移的描述。
- **触发是事件，所以部分的数目是开放的。** 新摊位通过声明该事件加入；场馆和编排摊位都不枚举应用的组成部分。
- **区域就是槽位，所以可以换掉某一块而不动外壳。** 岛帧只声明位置；谁填进去是平面上的路由问题。
- **单进程还是多进程都一样。** 每一步都是普通流量：别人写的、跑在别处的部分，对同一个事件给出同样的回答。

## 状态住在哪

| 持有者 | 它拥有什么 | 它绝不能持有 |
|--------|------------|--------------|
| 场馆 | 连接、设备、用户、token、被要求服务的路由 | 应用的词汇（一个模型、一条规则、一个设置） |
| 应用 | 它的行（在自己的命名空间里）、它的布局、它的事件词汇 | 场馆可达性事实的副本 |
| 页面 | token 和它收到的东西 | 任何持久真相——把真相存在页面里就是第二个真相来源 |
| 平台（aura） | 场域：类型、路由、应用声明的嵌入式存储 | 任何应用的业务策略 |

## 同一个应用的两种渲染

同一个应用可以对渲染器说话，也可以对程序说话。区别在**输出形状**，不是第二套实现：给只负责画的表面是帧，给读的程序是裸 delta。形状由调用方在入口处选择，形状里的名字由调用方声明，两者走同一条线——无论哪种，场馆都剥掉 `view:` 标记，于是程序看到的是它本来就在说的裸名字。

## 这个模型拒绝的东西

- 页面渲染它没有被交付的业务知识（字段、默认值、取值范围）——渲染器在结构上保持愚蠢。
- 传输层学会某个应用的词汇——prism 一旦知道「模型」是什么，每次应用改动都会变成网关改动。
- 为管理另造一个面——产品与其设置共用一套词汇、一套鉴权、一个客户端。
- 只以部署文件形式存在的布局，而它背后的应用本可以自己说出这份布局。
