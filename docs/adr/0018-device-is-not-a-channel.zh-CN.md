# 0018 — 设备是连接，频道是业务

状态：Accepted（2026-10-29）
取代：无。修正本仓早前设计记录与 2026-10-29 线协议改造中的一处说法——那里把 `channel_id` 当成了场馆概念。

## 背景

连接面（ADR-0017）给每条连接分配一个 **device** 号，并把它绑定到 **user** 账号。这两件事都在这里被验证：device 是连接建立时发的号，user 是注册表对 `login` 的回答，鉴权声明在投递之前作用于这两者。

线上还带着一个叫 `channel_id` 的字段。今天它写的是 device 号（`ui.rs`，场馆自己的话），读的时候又是拿去和接收连接的 device 比：

    if target.is_some_and(|t| t != c.device) { continue; }

那不是频道，是套了频道名字的设备号，而这个名字会把人引向错误模型。频道是**用户可见的分组**：群聊；一对一对话用的是同一套机制、两个成员，所以两者都叫频道。成员、创建（显式"建群"，或开始对某人说话时隐式产生）、事后拉人，以及这些东西到底存不存在，都是**应用**的性质而不是传输层的性质。有的应用只支持一对一，那就把两个人之间的对话存下来即可；有的只有群、没有一对一频道；wiki 里《液态化》描述的应用形态两者都不是，因为它的视图由一条连接打开、也在这条连接上被回答。

## 决定

1. **场馆只认识 device 和 user，身份模型到此为止。** 超出"这条连接"/"这个账号"的可达性，都是别人的状态。这一对是稳定部分：传输层变化才会改它，产品的取舍不会。

2. **频道是摊位的概念。** 做群聊的摊位把成员放在自己的命名空间里，按业务需要组织，并自己回答"这个群里都有谁"。prism 不知道群的存在，无法枚举，也从不校验成员关系。

3. **`channel_id` 不是场馆字段，退出线协议。** 分发是**地址**，不是成员判定：要发给多个收件人的事件，把收件人（device 号，或解析成 device 的 user）写出来。"发给频道 7 的所有人"只有拥有频道 7 的摊位才说得出，所以由摊位把群翻译成收件人列表。

4. **场馆仍然保证的，仅此而已**：device 号是一条活连接的地址；带锚点的号（`?device=`）能跨重连；device↔user 绑定归注册表；鉴权声明在投递发生之前生效；发方不会收到自己事件的分发回声。

## 后果

- 下行里那条 `channel_id` 比较消失，字段本身也消失。信封带 `sender` 和显式收件人；只有"打开这个视图的那条连接"的摊位，直接寻址那一个 device，命名任何分组都不需要。
- 创建频道不是场馆动词：这里不发号，不存成员。
- 需要群的应用在摊位里实现，存在摊位自己的存储里，用自己的规则——改这些规则不必碰传输层。
- 《液态化》形态一样都不需要：渲染器在自己的连接上打开视图，应用在同一条连接上回答，没有任何东西需要"成为其成员"。
- 按这个 ADR 直读，今天的线协议有一处会安静地错：一个遵守本 ADR 的摊位发 `channel_id: 7`，一个渲染器也收不到，因为 7 是拿去和 device 号比的。这正是本 ADR 要移除的缺陷，而不是要记录下来的设计。
