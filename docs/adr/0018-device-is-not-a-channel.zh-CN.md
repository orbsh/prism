# 0018 — 设备是连接，频道是业务

状态：Accepted（2026-10-29）。修正本仓早前设计记录与 2026-10-29 线协议改造中的一处说法——那里把 `channel_id` 当成了场馆概念。

## 背景

连接面（ADR-0017）给每条连接分配一个 **device** 号，并把它绑定到 **user** 账号。这两件事都在这里被验证：device 是连接建立时发的号，user 是注册表对 `login` 的回答，鉴权声明在投递之前作用于这两者。

线上还带着一个叫 `channel_id` 的字段，写的是 device 号（`ui.rs`，场馆自己的话），读的时候又是拿去和接收连接的 device 比：

    if target.is_some_and(|t| t != c.device) { continue; }

那不是频道，是套了频道名字的设备号，而这个名字会把人引向错误模型。频道是**用户可见的分组**：群聊；一对一对话用的是同一套机制、两个成员，所以两者都叫频道。成员、创建（显式"建群"，或开始对某人说话时隐式产生）、事后拉人，以及这些东西到底存不存在，都是**应用**的性质而不是传输层的性质。有的应用只支持一对一，那就把两个人之间的对话存下来即可；有的只有群、没有一对一频道；wiki 里《液态化》描述的应用形态两者都不是，因为它的视图由一条连接打开、也在这条连接上被回答。

## 决定

1. **场馆只认识 device 和 user，身份模型到此为止。** 超出"这条连接"/"这个账号"的可达性，都是别人的状态。这一对是稳定部分：传输层变化才会改它，产品的取舍不会。

2. **频道是摊位的概念，而且整个频道都归摊位。** 做群聊的摊位把成员放在自己的命名空间里，按业务需要组织，并自己回答"这个群里都有谁"。prism 不知道群的存在，无法枚举，也从不校验成员关系。把这个所有权画在一个常规聊天应用上就是：建视图时它向自己的存储问"这个成员在哪些频道里"，保留**当前激活**的那个和它的历史，按这个状态回答视图；切换频道就是同一个回答换一个激活项，跟场馆无关。它的 composer 是消息下方的一个 form，**唯一**的字段是说出口的话——**谁**在说是场馆盖的章（ADR-0017 §7：prism 给每个页面事件挂 `sender {device, user}`，存储侧的 member id 就是用户的 uuid），**说进哪个会话**是应用的激活频道，而不是一个页面能填的字段（否则页面就能替别人说话）。创建、邀请、频道列表都是应用的存储和应用的规则；场馆贡献的是 device↔user 绑定和寻址。

3. **`channel_id` 不是场馆字段，线协议两个方向都不带它。** 分发是**地址**，不是成员判定：要发给多个收件人的事件，把收件人（device 号，或解析成 device 的 user）写出来。摊位命名一个 USER，就是命名一个账号，把分发交给场馆——它枚举不了设备，所以跨设备投递只能由场馆做。"发给频道 7 的所有人"只有拥有频道 7 的摊位才说得出，所以由摊位把群翻译成收件人列表。发送一半已经是这个说法（gravity 的 turn 发 `{name, device, data}`，自己不写 sender），接收一半按 `device` 或 `user` 寻址——所以发那个已退役字段的摊位**到不了**任何渲染器，而不是靠巧合到达。要重新把那个字段读回来，那是一个新决定，不是兼容性问题。

4. **场馆仍然保证的，仅此而已**：device 号是一条活连接的地址；跨重连靠的是 TOKEN（号只命名设备，不证明任何东西）；device↔user 绑定归注册表；鉴权声明在投递发生之前生效；发方不会收到自己事件的分发回声。

5. **以模型为主的应用根本没有频道**，而这才这套栈要做的形态。gravity 的核心是一个人跟模型对话；当一个人需要另一个人时，**模型**开口——它发通知，协调长成《液态化》描述的形状：不约时间地点，按主题的拓扑把方案推给相关的人，人在自己已有的界面上回复或投票，系统整理、改方案、再推，迭代到收敛。加一个频道就是"会议改成群聊"——同一条链换个传输介质，那份文档恰恰拒绝了这一招，gravity ADR-0006 从平面层面论证了同一件事（每对一条维护中的频道，N(N-1)/2 条，每一条都是一场语义协商）。频道式的对话以后可以作为应用的一种选择加上去；它不是这个平面的要求。

6. **存储里的 `channel` 是容器，不是产品概念。** k10r 把回合、成员、会话放在一个频道号下面——那是应用写入的命名空间。只服务一段对话的部署给它一个号，然后从不展示它；这也是为什么回合可以带频道号，而人不带。

## 后果

- 下行里那条 `channel_id` 比较消失，字段本身也消失。信封带 `sender` 和显式收件人；只有"打开这个视图的那条连接"的摊位，直接寻址那一个 device，命名任何分组都不需要。
- 创建频道不是场馆动词：这里不发号，不存成员。
- 需要群的应用在摊位里实现，存在摊位自己的存储里，用自己的规则——改这些规则不必碰传输层。
- 《液态化》形态一样都不需要：渲染器在自己的连接上打开视图，应用在同一条连接上回答，没有任何东西需要"成为其成员"。
- 建在这个平面上的应用问不出"频道 7 里有谁"：它拿到的是 device↔user 绑定，和它自己拼出来的收件人列表，没有别的。
